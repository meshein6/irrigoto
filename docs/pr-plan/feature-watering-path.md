# Watering path: mode and depth, path preview, Sections, coverage and passes

**Branch:** `feature/watering-path` · **Type:** feature · **Cut from:** `main`
· **Status:** built and running on hardware as part of `combined`. Coverage
and passes are dry-verified only; wet test outstanding.

This is the one description for everything about *the path a run takes*: how
you choose the run, how you see the path before it runs, the order the rings
are visited in, how close the rings are, and how many passes lay the water
down. It replaces eight separate descriptions and two branches:

## Summary

- **Water modal:** pick **Mode**, **Depth** and **Passes** separately (any mode
  at any depth), with an ⓘ that explains each mode. Remembers the last choice
  per browser.
- **Path preview:** a thumbnail of the path the chosen mode will take, in the
  Water modal, on every schedule entry and in Zone Setup. Tap for a full-screen
  view with a scrubber that walks the nozzle along the path. One shared script,
  `/path.js`, draws all of them.
- **Zone Setup:** zoom the map to the zone, view controls moved onto the map,
  a path scrubber, and a **Ring coverage** picker (Standard / Fine / Finest).
- **Sections** watering mode (web digit 9, HA / schedule index 4): serpentine
  motion, but it finishes one side of the zone outer → inner before crossing to
  the next, instead of crossing on every ring.
- **Passes** on the run, with the sweep speed solved from depth ÷ passes and a
  live `/api/run_plan` check that says, before the run starts, when the
  combination cannot be met and which pass count would.
- **Serpentine leg cap** raised 256 → 384 (DRAM paid for by shrinking
  `storage_make_room`'s list), and truncation is now a loud WARN.
- **Pulse** no longer overshoots every arc bound by up to ~3.6°.

## 1. Manual run: mode and depth pickers

**Problem.** The device's Water modal offered fixed presets (1/8″, 1/4″,
1/8″×2, Gentle 1/8″, …). There was no way to run e.g. Smooth 1/2″ by hand,
though schedule entries, Home Assistant and `POST /zone/water` (`mode=` +
`depth=` in eighths) all already supported it.

**Change (`landing.html`).**
- The preset grid becomes three pickers: **Mode** (Pulse · Gentle · Smooth ·
  Serpentine · Sections · Chase · Demo), **Depth** (1/8″ … 1″) and **Passes**
  (1 … 8; see §5).
- Demo hides Depth. Chase hides Depth and shows its duration slider.
- It sends the same web digits HA and the scheduler use: Pulse=1, Gentle=5,
  Smooth=7, Serpentine=8, Sections=9, Demo=`d`, Chase=`c`, plus `depth=` and
  `passes=` (neither for Demo/Chase).
- ⓘ next to Mode opens a description of the selected mode (tap, not hover, so
  it works on phones).
- The last mode / depth / passes are remembered in `localStorage` (in
  try/catch).

## 2. Zone Setup map zoom

**Problem.** The map was always scaled to the unit's full calibrated throw
(`_edScale()` = `act_max_throw + 914` mm), so a ~10 ft zone on a ~28 ft unit
was a cluster in the middle with overlapping labels.

**Change (`zone_setup.html`).**
- A **Zoom** toggle (`full` / `zone`), remembered in `localStorage`. Zoomed,
  `_edScale()` returns the zone's extent × 1.15 (floored at 1.2 m). Everything
  draws through `_edScale()`: rings, grid, points, path, heatmap, trail and the
  edit hit test.
- Grid labels step 1/2/5/10 ft to suit the visible range.
- The live throw ring and dot are clipped at the rim when the spray reaches
  past the view, and the dot gets a "27.6′ →" label.
- Edit-mode drags clamp to the full reach, not the zoomed range.
- Zoom, Path and Depth buttons now sit on the map instead of in the action row.

## 3. Path preview per mode

**Change.**
- **`html/path.js`**, served as `/path.js` (`path_js.h`, regenerated by
  `regen.py`, which now also handles `*.js` → `*_js.h` and syntax-checks them).
  `IrrigotoPath.build / draw / thumb / flatten / marker / openPreview` hold the
  ring and arc geometry once, for all three pages.
  - It mirrors the firmware's ring ladder (zone min/max, spacing rule, inner
    rings for a sprinkler inside the zone) and clips arcs to the polygon.
  - It draws each mode's real order and direction:

    | Mode | Ring order | Direction | Between rings |
    | --- | --- | --- | --- |
    | Pulse | outer → inner | always CW | dry swing back |
    | Gentle | outer → inner | flips each pass | dry swing back |
    | Smooth | chosen at run time; drawn outer → inner | per pass | dry swing back |
    | Serpentine | alternates out→in / in→out per pass | flips every ring | wet boundary-hugging turn |
    | Sections | lobe by lobe, outer → inner | flips every ring | wet turn; one dry hop between lobes |

  - Lobes are taken from the ring with the **most** arcs, mirroring the
    firmware planner (a zone with a waist is one arc at the outside and splits
    inward).
  - `normPoints()` accepts both `{deg, throw_mm}` (`/zone/state`) and
    `{deg, mm}` (`/api/all`). Reading only `throw_mm` used to draw an empty
    circle everywhere except Zone Setup.
- **Where it shows.** Under the pickers in the Water modal; one thumbnail per
  schedule entry, drawn lazily with `IntersectionObserver` (up to 32 entries);
  and in Zone Setup's Path view with a scrubber.
- **One full-screen overlay**, shared by all three. The Water modal and
  schedule entries **lock** it to the mode that will actually run; Zone Setup
  leaves the mode chips live for comparing modes.
- **Pass control (was `fix/preview-pass-count`).** The preview used to offer
  "Pass 1..4", a number nothing in the firmware uses, and for Serpentine and
  Sections a wrong pass index drew the sweep going the wrong way. Both the
  overlay and the Zone Setup chip now show the only thing that differs between
  passes: the direction ("Outer → in" / "Inner → out", or "Sweep one way" /
  "Sweep back"). They are hidden for Pulse, Chase and Demo, where every pass
  looks the same.
- **Caching.** `/path.js` is served `no-cache, must-revalidate`. A day-long
  `max-age` meant a browser held yesterday's script after a firmware update and
  showed no preview for a new mode. When the script is stale the page now says
  so instead of silently drawing Pulse's path for every mode.

## 4. Sections mode

**Why a mode and not a zone setting.** A per-zone **Ring order** setting
(`feature/ring-order`: Auto / one ring at a time / section by section) was
built and then removed. It only meant anything for two of the five modes
(Pulse and Gentle already walk outer → inner), it made a *run* property a
*zone* property, so the same zone could not be watered two ways without
editing it, and "section by section" was serpentine-only while sitting in a
setting that claimed to apply to everything. The per-zone field, NVS key,
storage code and picker are gone, and Smooth's scheduler is unconditional
again.

**Change.** Sections is a watering mode, encoded like every other mode:

| Site | Value |
| --- | --- |
| Web digit (`/zone/water mode=`) | `9` |
| HA mode select / schedule `mode` | `4` (`"Sections"`) |
| `phase_water_zone` selector | `'e'` |

- It shares every serpentine code path. Only `serpentine_build_pass_plan`
  (new `sections` argument) changes the emission order: it finds the lobes,
  then emits lobe-major (finish one side outer → inner, then the next), so
  cross-zone jumps drop from (lobes − 1) × rings to (lobes − 1).
- An arc on an inner ring belongs to the lowest-index lobe it overlaps
  (`serp_arc_overlaps`), so merged inner rings are swept once.
- The move to a new lobe is forced **dry** (the previous exit is dropped), so
  the connector does not water its way across the zone with a 30-waypoint
  boundary hug.
- With a single lobe it quietly falls back to Serpentine, which never crosses
  anyway.
- Also: `esphome/irrigoto-core.yaml` now lists **Serpentine** and **Sections**
  in the HA mode select. Serpentine had been published since upstream b431 but
  was never listed, so the publish was rejected.
- Schedule text (`set_text` / `sync_text`) accepts mode 4; the duration
  estimate treats it like Serpentine; `irrigoto_get_mode` / `get_status` /
  `last_water_mode_label` know it.

## 5. Coverage on the zone, passes on the run

Owner design, 2026-09-26: *"I should get coverage settings in the zone config
and then for an actual run I should be able to control the depth and number of
passes which calculates a speed for you. Make sure to bound these two
variables to avoid creating runs that are too fast."*

- **Coverage** (how close the rings sit) belongs to the **zone**: it follows the
  zone's size and shape, not the run.
- **Depth and passes** belong to the **run**.
- **Speed is not a knob.** The firmware already solves it:
  `serpentine_ring_dps()` and the shared ring loop turn a per-pass deposit
  target into degrees per second, clamped to the speed map.

### Coverage (density)

- `zone_perimeter_t.coverage`: 0 Standard / 1 Fine / 2 Finest. It is saved in
  the zone JSON and read by `storage_zone_parse_json`, so imports keep it.
  Missing reads as Standard. `zone_load_nvs` zeroes the struct first, so an
  older, shorter NVS blob leaves the new byte at Standard.
- It scales `WATER_RING_SPACING` (700 mm × throw / max throw, floored at 80 mm):

  | Setting | Scale | Rings on a 3.3 m zone |
  | --- | --- | --- |
  | Standard | × 1.00 | ~18 |
  | Fine | × 0.75 | ~23 |
  | Finest | × 0.50 | ~29 |

- Pitch and footprint move together: `s_ring_pitch_mm` feeds all four
  ring-generation sites and `s_ring_footprint_mm` all three footprint
  tolerances. `water_run_t.ring_footprint_mm` records what a run used, so
  `ring_covers()` does not double-count overlap on a Finest run (a pre-change
  run file reads 0 and keeps the old width).
- Zone Setup: a **Ring coverage** row with a one-line note per option.
  `/zone/act?cmd=set_coverage&v=` sets it, and the next Save writes it.
  `/zone/state` reports `coverage`.

### Passes

- `POST /zone/water … &passes=1..8`, consumed once by `phase_water_zone` like
  depth. Absent or 0 means each mode's own behaviour, so HA and old clients are
  unaffected.
- `per_pass_target = depth_mm / passes` goes to the speed solver in both paths:
  the shared ring loop and `serpentine_build_pass_plan` (new
  `water_serpentine_passes` argument). Fewer passes means a slower, heavier
  sweep. Pulse, whose pass *is* its depth unit, takes the request as its pass
  count outright.

### The bound, made visible

The clamp fails silently in both directions:

- **pinned at max dps**: the sweep cannot go fast enough, every pass
  over-applies, and the run overshoots. Too many passes for the depth.
- **pinned at min dps**: the sweep cannot go slow enough, and the target is
  never met. Too few passes for the depth.

`GET /api/run_plan?zone=&depth=&passes=` walks the same ring ladder at the
zone's coverage, asks the solver for each ring's speed, and returns the clamp
state, the dps range, the estimated minutes, and the **smallest pass count
that clears the clamp** (searched, not guessed). The Water modal shows this
live under the pickers: speed and minutes when it works, and which way it is
wrong and what to change when it does not.

This unit's `speed.json` has `min_continuous_dps: 0.00`, so the slow side has
no real floor. `/api/run_plan` judges against a conservative 10.9 dps, reports
`speed_floor_cal: false` and says so in the advice.

Measured plan output (zone 0, 237° arc, 20 rings, Standard):

```
depth  passes  per_pass   dps range      clamp  suggest  est_min
1/8    1       3.17 mm    10.9-10.9      slow   3        7.2
1/8    2       1.59 mm    10.9-11.4      slow   3       14.4
1/8    4       0.79 mm    10.9-22.8      none   3       20.8
2/8    8       0.79 mm    10.9-22.8      none   6       41.6
8/8    8       3.17 mm    10.9-10.9      slow   0       57.9
```

The 7.2 min estimate for 1/8″ × 1 compares with a measured 5.9 min. The last
real 1/8″ run delivered `actual_avg_depth_mm 1.53` against 3.175, which is the
"too few passes" failure the endpoint now reports.

## 6. Smaller path fixes

- **Serpentine leg cap 256 → 384.** A measured 20-ring run hit the cap at ring
  13 and never watered the outer third. The 4 KB comes from cutting
  `storage_make_room()`'s static list from 200 to 64 entries (−8.5 KB; it
  already loops until enough space is free). Truncation is now a WARN that says
  part of the zone will not be watered. 384 is still not enough for Finest on a
  large zone (~580 legs); see Open work.
- **Pulse arc-bound overshoot.** Each pulse was a fixed ~3.9° shove, fired
  whenever 0.3° remained, so every arc ended up to ~3.6° (~200 mm at 3.2 m)
  outside the polygon with the valve open. The final pulse is now scaled to
  land on the bound (or skipped below a third of a pulse), and only full-length
  pulses update the learned step size.

# Deterministic rebuild (b569-b586)

Owner decision after using the adaptive version: *"stop all of this old logic.
Use the planned paths exactly as is"*, *"make sure each pass is ACTUALLY known
in advance"*, *"run as many as needed to get the outcome"*.

## The plan decides the run

The pass schedule is computed **once, before any water flows**, from the
executor's own functions:

```
dps = serpentine_ring_dps(...)          the speed that will be used
d1  = nozzle_precip_depth_mm(..., dps)  what one sweep deposits
n   = ceil(target / d1)                 passes that ring needs
```

`skip[]` reads that schedule instead of `cumulative_depth`. `corr` is seeded
from the previous run and then held. The throw-retry re-fire and the pass-0
un-credit are gone. Measurement still happens and is still logged — it no
longer changes the plan. The full schedule is logged per ring at run start.

Determinism makes passes **predictable, not absent**: outer rings still do not
reach target in one pass at the speed floor, so the plan schedules two or
three and says which rings, up front.

## Three bugs found by looking at a real run's log

**Depth was double-counted on multi-arc rings.** `nozzle_precip_depth_mm`
returns the depth on the wedge just swept — the arc cancels, because a shorter
sweep takes proportionally less time over proportionally less ground. Adding
it once per wedge into a per-**ring** counter claims the same ground was
watered twice. Measured, ring 20 inside a *single* pass:

```
r20 sweep 35.8 deg ... cum 2.29mm      <- lobe A
r20 sweep 42.4 deg ... cum 5.20mm      <- lobe B
```

against a 3.175 mm target, after which the firmware dropped r20 from pass 2
while each lobe had received about 2.5 mm. Every multi-arc ring was
under-watered by roughly its arc count. Credit is now weighted by arc share.
(The shared Gentle/Smooth loop never had this — it credits once per ring per
pass, which is the correct semantics.)

**The valve tolerance swallowed most ring steps.** The ladder moves the valve
0.43–0.97 deg between consecutive rings. `V_TOL_DEG` was 0.8, so

```c
if (v_abs < V_TOL_DEG) { stop }
```

declared the valve already in position for **13 of 19** transitions: it never
moved, and consecutive rings swept the same physical distance. This is the
"goes back and forth at the same distance" and "distances aren't adjusting
granularly" reports. Tolerance 0.8 → 0.20 (the encoder resolves 0.088 deg),
decel band 4.0 → 1.0, and the ramp floor lifted off the stall threshold — a
sub-degree step used to spend its entire travel in the easing ramp, which
computes duty ~76, the duty b521 records this valve stalling at. 19 of 19
transitions now command a move the chase executes.

**Lobes were ordered by bearing.** `serpentine_arc_bounds` returns arcs sorted
by CW distance from the zone arc start, so the run began with whichever lobe
came first round the circle — on the measured zone the 260–340 deg lobe, which
only reaches ring 19. The run started mid-distance, worked in to ring 31, then
jumped to the other lobe and started again at ring 1. Each lobe was correctly
outer→inner; the lobes were in the wrong order. Now sorted by reach, in the
firmware **and** in `path.js` — they have to agree or the preview starts on
the opposite side.

## Valve control

`serp_valve_settle_from_below` is gone. It drove the valve past a ring's
target and back up so the ball always landed from the same side — with the
stream ON, so every inward ring change sprayed short for up to 1.5 s. Its real
job was getting a stuck ball moving; a bounded stiction pulse does that
without ever leaving the planned distance (fires after 90 ms of no encoder
movement, lasts 100 ms at duty 420, at most 10 per leg, so a jammed valve
still reaches the existing fault paths).

The first wet sweep waits for pressure to actually stabilise rather than a
fixed 1800 ms — two consecutive reads agreeing, capped at 9 s. The
reach-ordering means the run now starts on the outermost ring, the one least
tolerant of a supply still coming up.

## Preview and run are one artifact

- Coverage reaches **every** preview entry point (it previously reached two of
  five, which is why Sections looked unaffected by it).
- Serpentine/Sections turns are drawn as the wet boundary-hug glides they are;
  `dryReturn` was a guess and is gone.
- The scrubber plays the **whole multipass run** from the firmware's own
  `ring_passes`, so the play button plays what will happen.
- `run_plan` counts passes with the run's own deposit expression, not a clamp
  ratio. Those are algebraically equal only while the solver uses the plain
  annulus area; below `WATER_MIN_ELLIPSE_THROW_MM` it substitutes a splash
  band, and the preview predicted four passes where the run did two.
- Zone Setup shows **rings only** — where the water goes. How the nozzle
  travels them belongs to a run.

Measured after alignment: `passes 2`, `est_min 4.9` against an observed 1.5–2
passes and a 4.7 min run.

## Live view

`/api/status` publishes planned and actual throw separately (conflating them
hid the very thing being looked for), plus the run's shape. A **Live** chip in
the watering bar opens the shared overlay on demand: planned path, a dashed
circle at the ring the plan says the nozzle is on, live marker on top — a
short throw reads as the dot inside the circle. Polls at 0.5 s while open.

## Diagnostics

The 24 KB log ring drops the **oldest** bytes, and the oldest bytes are the
plan. 1.5 KB of pinned head now survives the wrap in both the served and the
persisted copy, so a completed run's log still carries its schedule.

## Review pass (b587-b593)

### There were two ring ladders

`/api/all` never published `act_max_throw` or `act_min_throw`, though
`/zone/state` always has. So `path.js` fell back to its built-in 10058 mm
where this unit's calibration says **8424** — a 16% error in the ring pitch,
on every page that draws a ladder. The Water modal drew **34 rings** under a
plan note that said **31**.

Publishing the two numbers fixes the fallback, but the real problem was
having two ladders at all. Where the firmware has published `ring_mm`, the
preview now draws **that**, and a ring scheduled for zero passes is dropped
rather than drawn as an arc that never animates. b573's nearest-radius pass
matching existed only to reconcile two ladders that should never have been
built separately; it is gone.

Captions counted ring *visits*, so Sections reported 42 where the ladder has
30 — `geom.ringCount` is the distinct count. `run_plan`'s advice paired a
waterable-only numerator with an all-rings denominator; it counts waterable
rings now (`rings_wet`).

### The estimate was twice the measured run

The preview summed sweeps only; the executor also charged 2.5 s per
ring-pass and a 25 s tail. Making them agree made both wrong:

| | 31-ring Sections @ 1/8" |
|---|---|
| measured (b583, b573) | **3.4 min, 4.1 min** |
| model, sweeps only | 4.9 min |
| model + overhead + tail | 7.1 min |

The sweep term *alone* (294 s) exceeds the whole measured run (206 s), so no
overhead term reconciles them: `run_plan_active_deg` integrates over wider
arcs than `serpentine_arc_bounds` actually sweeps. **That is still open** —
diagnosing it needs a run to compare against.

What is fixed is which number gets quoted. b578 replaced a history-anchored
estimate with the model for serpentine and sections; pulse, gentle and smooth
never stopped preferring history (b298: *"when we have history, history
wins"*). `water_est_run_secs()` restores that rule for the deterministic
modes and is called by **both** the executor and the preview — one answer,
**3.6 min** against measured 3.4–4.1. The page says which source it used.

### The live view drew the wrong plan

It reached for whatever `/api/run_plan` last returned for the Water modal's
selection — the wrong zone for a scheduled run, or `null` if the modal was
never opened, in which case it drew one lap over a multi-pass run. The
executor now publishes the schedule it is executing (`/api/live_plan`), fixed
at run start, fetched once. The schedule editor's full-screen preview also
shows the whole run rather than a single lap.

The live poll rescheduled itself on a truthy timer handle, so reopening the
view while a fetch was in flight left **two** loops running and doubled the
poll rate for the rest of the run.

### Geometry

Every test re-derived each vertex from `(deg, throw_mm)` with its own `sin`
and `cos` — about **440,000** sin/cos pairs to draw one picture, all the same
nine answers. Projecting the polygon once takes a build from **4.9 ms to
0.8 ms**, verified identical across 60 mode × zone × coverage combinations.
That is what the Zone Setup d-pad was waiting on between steps.

`flatten()` measured sweeps with `angDelta`, which folds anything over 180°
back into ±180°: a 237° lobe was timed as 123°, and a **full-circle ring
folded to exactly 0** and fell through to the 1 mm floor — the marker crossed
a whole ring in one frame. It uses the span. Playback was a flat ~8 s however
long the run, so the longer the real run the faster its preview; it scales.

Also removed: the pass-stepper the scrubber replaced in b569 (dead since),
and the second `build()` each caller did to caption a picture it had already
drawn.

## Still open

- **The flow constant.** `NOZZLE_FLOW_K = 4542` at `N = 0.566` is what the
  schedule rests on (`ceil(target / predicted_deposit)`). Planner and executor
  share it, so they agree with each other — that does not make it right. If a
  run reaches its scheduled passes and the ground is dry, this is why.
- **Transition overhead.** Sweeps totalled ~60 s of a 247 s run before the
  valve-control work; worth re-measuring now.
- **The 80 mm ring-spacing floor** makes Standard and Finest identical below
  3.2 ft.
- **Pulse / Gentle / Smooth are unchanged** and still adaptive. Their preview
  and estimate are a model, not their behaviour.
