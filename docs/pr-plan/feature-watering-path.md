# Watering path: mode and depth, path preview, Sections, coverage and passes

**Branch:** `feature/watering-path` · **Type:** feature · **Cut from:** `main`
· **Status:** built and running on hardware as part of `combined`. Coverage
and passes are dry-verified only; wet test outstanding.

This is the one description for everything about *the path a run takes*: how
you choose the run, how you see the path before it runs, the order the rings
are visited in, how close the rings are, and how many passes lay the water
down. It replaces eight separate descriptions and two branches:

## Summary

- **Water modal:** pick **Mode**, **Depth** and **Passes** separately (any mode
  at any depth), with an ⓘ that explains each mode. Remembers the last choice
  per browser.
- **Path preview:** a thumbnail of the path the chosen mode will take, in the
  Water modal, on every schedule entry and in Zone Setup. Tap for a full-screen
  view with a scrubber that walks the nozzle along the path. One shared script,
  `/path.js`, draws all of them.
- **Zone Setup:** zoom the map to the zone, view controls moved onto the map,
  a path scrubber, and a **Ring coverage** picker (Standard / Fine / Finest).
- **Sections** watering mode (web digit 9, HA / schedule index 4): serpentine
  motion, but it finishes one side of the zone outer → inner before crossing to
  the next, instead of crossing on every ring.
- **Passes** on the run, with the sweep speed solved from depth ÷ passes and a
  live `/api/run_plan` check that says, before the run starts, when the
  combination cannot be met and which pass count would.
- **Serpentine leg cap** raised 256 → 384 (DRAM paid for by shrinking
  `storage_make_room`'s list), and truncation is now a loud WARN.
- **Pulse** no longer overshoots every arc bound by up to ~3.6°.

## 1. Manual run: mode and depth pickers

**Problem.** The device's Water modal offered fixed presets (1/8″, 1/4″,
1/8″×2, Gentle 1/8″, …). There was no way to run e.g. Smooth 1/2″ by hand,
though schedule entries, Home Assistant and `POST /zone/water` (`mode=` +
`depth=` in eighths) all already supported it.

**Change (`landing.html`).**
- The preset grid becomes three pickers: **Mode** (Pulse · Gentle · Smooth ·
  Serpentine · Sections · Chase · Demo), **Depth** (1/8″ … 1″) and **Passes**
  (1 … 8; see §5).
- Demo hides Depth. Chase hides Depth and shows its duration slider.
- It sends the same web digits HA and the scheduler use: Pulse=1, Gentle=5,
  Smooth=7, Serpentine=8, Sections=9, Demo=`d`, Chase=`c`, plus `depth=` and
  `passes=` (neither for Demo/Chase).
- ⓘ next to Mode opens a description of the selected mode (tap, not hover, so
  it works on phones).
- The last mode / depth / passes are remembered in `localStorage` (in
  try/catch).

## 2. Zone Setup map zoom

**Problem.** The map was always scaled to the unit's full calibrated throw
(`_edScale()` = `act_max_throw + 914` mm), so a ~10 ft zone on a ~28 ft unit
was a cluster in the middle with overlapping labels.

**Change (`zone_setup.html`).**
- A **Zoom** toggle (`full` / `zone`), remembered in `localStorage`. Zoomed,
  `_edScale()` returns the zone's extent × 1.15 (floored at 1.2 m). Everything
  draws through `_edScale()`: rings, grid, points, path, heatmap, trail and the
  edit hit test.
- Grid labels step 1/2/5/10 ft to suit the visible range.
- The live throw ring and dot are clipped at the rim when the spray reaches
  past the view, and the dot gets a "27.6′ →" label.
- Edit-mode drags clamp to the full reach, not the zoomed range.
- Zoom, Path and Depth buttons now sit on the map instead of in the action row.

## 3. Path preview per mode

**Change.**
- **`html/path.js`**, served as `/path.js` (`path_js.h`, regenerated by
  `regen.py`, which now also handles `*.js` → `*_js.h` and syntax-checks them).
  `IrrigotoPath.build / draw / thumb / flatten / marker / openPreview` hold the
  ring and arc geometry once, for all three pages.
  - It mirrors the firmware's ring ladder (zone min/max, spacing rule, inner
    rings for a sprinkler inside the zone) and clips arcs to the polygon.
  - It draws each mode's real order and direction:

    | Mode | Ring order | Direction | Between rings |
    | --- | --- | --- | --- |
    | Pulse | outer → inner | always CW | dry swing back |
    | Gentle | outer → inner | flips each pass | dry swing back |
    | Smooth | chosen at run time; drawn outer → inner | per pass | dry swing back |
    | Serpentine | alternates out→in / in→out per pass | flips every ring | wet boundary-hugging turn |
    | Sections | lobe by lobe, outer → inner | flips every ring | wet turn; one dry hop between lobes |

  - Lobes are taken from the ring with the **most** arcs, mirroring the
    firmware planner (a zone with a waist is one arc at the outside and splits
    inward).
  - `normPoints()` accepts both `{deg, throw_mm}` (`/zone/state`) and
    `{deg, mm}` (`/api/all`). Reading only `throw_mm` used to draw an empty
    circle everywhere except Zone Setup.
- **Where it shows.** Under the pickers in the Water modal; one thumbnail per
  schedule entry, drawn lazily with `IntersectionObserver` (up to 32 entries);
  and in Zone Setup's Path view with a scrubber.
- **One full-screen overlay**, shared by all three. The Water modal and
  schedule entries **lock** it to the mode that will actually run; Zone Setup
  leaves the mode chips live for comparing modes.
- **Pass control (was `fix/preview-pass-count`).** The preview used to offer
  "Pass 1..4", a number nothing in the firmware uses, and for Serpentine and
  Sections a wrong pass index drew the sweep going the wrong way. Both the
  overlay and the Zone Setup chip now show the only thing that differs between
  passes: the direction ("Outer → in" / "Inner → out", or "Sweep one way" /
  "Sweep back"). They are hidden for Pulse, Chase and Demo, where every pass
  looks the same.
- **Caching.** `/path.js` is served `no-cache, must-revalidate`. A day-long
  `max-age` meant a browser held yesterday's script after a firmware update and
  showed no preview for a new mode. When the script is stale the page now says
  so instead of silently drawing Pulse's path for every mode.

## 4. Sections mode

**Why a mode and not a zone setting.** A per-zone **Ring order** setting
(`feature/ring-order`: Auto / one ring at a time / section by section) was
built and then removed. It only meant anything for two of the five modes
(Pulse and Gentle already walk outer → inner), it made a *run* property a
*zone* property, so the same zone could not be watered two ways without
editing it, and "section by section" was serpentine-only while sitting in a
setting that claimed to apply to everything. The per-zone field, NVS key,
storage code and picker are gone, and Smooth's scheduler is unconditional
again.

**Change.** Sections is a watering mode, encoded like every other mode:

| Site | Value |
| --- | --- |
| Web digit (`/zone/water mode=`) | `9` |
| HA mode select / schedule `mode` | `4` (`"Sections"`) |
| `phase_water_zone` selector | `'e'` |

- It shares every serpentine code path. Only `serpentine_build_pass_plan`
  (new `sections` argument) changes the emission order: it finds the lobes,
  then emits lobe-major (finish one side outer → inner, then the next), so
  cross-zone jumps drop from (lobes − 1) × rings to (lobes − 1).
- An arc on an inner ring belongs to the lowest-index lobe it overlaps
  (`serp_arc_overlaps`), so merged inner rings are swept once.
- The move to a new lobe is forced **dry** (the previous exit is dropped), so
  the connector does not water its way across the zone with a 30-waypoint
  boundary hug.
- With a single lobe it quietly falls back to Serpentine, which never crosses
  anyway.
- Also: `esphome/irrigoto-core.yaml` now lists **Serpentine** and **Sections**
  in the HA mode select. Serpentine had been published since upstream b431 but
  was never listed, so the publish was rejected.
- Schedule text (`set_text` / `sync_text`) accepts mode 4; the duration
  estimate treats it like Serpentine; `irrigoto_get_mode` / `get_status` /
  `last_water_mode_label` know it.

## 5. Coverage on the zone, passes on the run

Owner design, 2026-09-26: *"I should get coverage settings in the zone config
and then for an actual run I should be able to control the depth and number of
passes which calculates a speed for you. Make sure to bound these two
variables to avoid creating runs that are too fast."*

- **Coverage** (how close the rings sit) belongs to the **zone**: it follows the
  zone's size and shape, not the run.
- **Depth and passes** belong to the **run**.
- **Speed is not a knob.** The firmware already solves it:
  `serpentine_ring_dps()` and the shared ring loop turn a per-pass deposit
  target into degrees per second, clamped to the speed map.

### Coverage (density)

- `zone_perimeter_t.coverage`: 0 Standard / 1 Fine / 2 Finest. It is saved in
  the zone JSON and read by `storage_zone_parse_json`, so imports keep it.
  Missing reads as Standard. `zone_load_nvs` zeroes the struct first, so an
  older, shorter NVS blob leaves the new byte at Standard.
- It scales `WATER_RING_SPACING` (700 mm × throw / max throw, floored at 80 mm):

  | Setting | Scale | Rings on a 3.3 m zone |
  | --- | --- | --- |
  | Standard | × 1.00 | ~18 |
  | Fine | × 0.75 | ~23 |
  | Finest | × 0.50 | ~29 |

- Pitch and footprint move together: `s_ring_pitch_mm` feeds all four
  ring-generation sites and `s_ring_footprint_mm` all three footprint
  tolerances. `water_run_t.ring_footprint_mm` records what a run used, so
  `ring_covers()` does not double-count overlap on a Finest run (a pre-change
  run file reads 0 and keeps the old width).
- Zone Setup: a **Ring coverage** row with a one-line note per option.
  `/zone/act?cmd=set_coverage&v=` sets it and **persists it immediately** —
  requiring a Save meant the preview and the run disagreed until the user
  pressed it, and Save also drops the cached heatmap, far too heavy for a
  settings tap. The heatmap stays valid regardless because every run records
  the footprint it used.
- **The preview draws the real pitch.** `ringThrows()` in `path.js` had the
  700 mm base hardcoded, so it drew Standard spacing whatever the zone was set
  to: changing coverage appeared to do nothing, and the preview claimed a ring
  layout the firmware would not use. It now scales by `coverageScale()`,
  mirroring `zone_coverage_scale()`, with the 80 mm floor left unscaled to
  match `WATER_MIN_RING_SPACING`. Coverage rides in `/api/all`'s zone payload
  and in `/zone/state`, so both the Water modal thumbnail and the Zone Setup
  canvas follow it, and Zone Setup redraws on the tap.

### Passes: removed, and replaced by "as slow as the nozzle can hold"

b557 shipped a 1..8 pass picker exactly as the design above asked. Owner
direction after using it, 2026-09-27: *"get rid of pass selection, always
optimise for slowest possible travel. Make sure we go as slow as possible for
the angle sweep."*

That is right, and it supersedes the design. A chosen pass count is a guess at
a number the firmware can solve for, and slow is what we want anyway: every
extra pass repeats the ring transitions, which is where the travel waste and
the stream wander live (`feature-depth-by-speed.md` asked for this first).

- Every pass now asks for the **whole** target depth, so the solver returns
  the slowest sweep it can and the floor clamp is the only thing stopping it
  asking for one the nozzle cannot hold. The pass count falls out: the
  adaptive multipass tops up, per ring, whatever one slow pass did not reach.
- **Gentle is exempt.** It exists for seed and bare soil, where a heavy slow
  pass is the failure mode rather than the goal, so it keeps
  `GENTLE_PER_PASS_DEPTH_MM`. A first cut of this override removed that;
  caught before it shipped.
- `POST /zone/water&passes=` is accepted and ignored; nothing in the UI asks.

### The bound, made visible

The clamp fails silently in both directions:

- **pinned at max dps**: the sweep cannot go fast enough, so even one pass
  over-applies and the run overshoots. Depth is the only lever left.
- **pinned at min dps**: the sweep cannot go slow enough, so one pass falls
  short and the run needs more of them.

`GET /api/run_plan?zone=&depth=` walks the same ring ladder at the zone's
coverage and reports what the firmware solved: the dps range, the fraction of
the target one slow pass reaches (`pass_frac`), the pass count that implies,
and the estimate. The Water modal shows it live under the depth picker.

Two things had to be fixed to make that honest:

- `spd_load_primary()` falls back to the slowest **measured** speed when the
  stored `min_continuous_dps` is <= 0. This unit stored 0.00 while the same
  file lists 10.25 deg/s, so `serpentine_ring_dps` clamped nothing below and
  Serpentine/Sections were commanding sub-stall speeds — a stall, reported as
  a completed run.
- `serpentine_ring_dps_ex()` exposes the **pre-clamp** requested speed.
  Without it `run_plan` compared the clamped return against itself and
  reported every depth reaching 100 % of target in one pass — confidently
  wrong.

### What the honest numbers say

```
coverage  rings   1/8" sweep        one pass reaches   passes
Standard   20     10.2 deg/s              26%            4
Fine       25     10.2 deg/s              30%            4
Finest     31     10.2-11.4 deg/s         30%            4

depth   one pass   passes
1/8       26%         4
2/8       13%         8
4/8        7%        16
8/8        3%        31
```

**At the slowest sweep the nozzle can hold, one pass delivers about a quarter
of a 1/8″ target.** The mechanism is roughly 4× too fast at its floor for this
zone. No pass count fixes that well — 1/2″ would want 16 passes — and it is
corroborated by the last real run: `actual_avg_depth_mm 1.53` against a 3.175
target, 48 %, reported at the time as simply "completed".

Note that finer coverage helps only slightly (26 % -> 30 %), and only through
the smaller per-ring annulus. The large effect — closer rings overlapping so
their depths add — is precisely what a pitch-tied footprint cannot represent.
See "Open work".

## 6. Smaller path fixes

- **Serpentine leg cap 256 → 384.** A measured 20-ring run hit the cap at ring
  13 and never watered the outer third. The 4 KB comes from cutting
  `storage_make_room()`'s static list from 200 to 64 entries (−8.5 KB; it
  already loops until enough space is free). Truncation is now a WARN that says
  part of the zone will not be watered. 384 is still not enough for Finest on a
  large zone (~580 legs); see Open work.
- **Pulse arc-bound overshoot.** Each pulse was a fixed ~3.9° shove, fired
  whenever 0.3° remained, so every arc ended up to ~3.6° (~200 mm at 3.2 m)
  outside the polygon with the valve open. The final pulse is now scaled to
  land on the bound (or skipped below a third of a pulse), and only full-length
  pulses update the learned step size.

## Open work

- **Passes on schedule entries.** Only manual runs carry `passes=`. Needs a
  schedule schema bump with an NVS migration, plus the HA package.
- **Slow-sweep floor.** When the target needs a slower sweep than the motor can
  hold, Gentle / Smooth under-deliver and Serpentine / Sections command
  sub-stall speeds (`min_continuous_dps` was 0 here; b561 falls back to the
  slowest measured speed, so this part is done). Pulse already escapes by
  dwelling. In order:
  1. Fall back to `deg_per_sec[0]` when the stored floor is ≤ 0.
  2. Run `phase_jog_pulse_cal()` so the pulse step is ~0.2° instead of ~3.9°.
  3. Plan below-floor rings as pulse-and-dwell (Serpentine / Sections per ring;
     opt-in for Gentle / Smooth).
  4. **Fix the footprint model:** depth should use the real stream width W, not
     the ring pitch. Today Finest coverage is credited the same depth as
     Standard, so coverage cannot help reach a target at all.
- **Depth by speed.** Owner preference: more depth should mean a slower sweep,
  not more laps. Passes now make that choosable per run; the remaining question
  is the default, which needs a wet test at 1/2″ and 1″ for runoff.
- **Leg budget for Finest.** 29 rings want ~580 serpentine legs; needs the
  shared-arena refactor (note: `mr_buf` cannot overlap the Smooth accumulator).
- **Exact preview.** `GET /zone/plan?id=&mode=&depth=&pass=` returning the
  firmware's actual leg list would make the preview exact rather than a mirror.
